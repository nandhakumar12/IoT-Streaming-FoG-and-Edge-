\begin{abstract}
Modern industrial environments generate continuous, high-frequency sensor
streams that quickly overwhelm conventional cloud-centric monitoring
architectures.
This paper presents \textbf{EdgeGuardian}, a fully containerised three-tier
AIoT platform that addresses this challenge by placing an intelligent,
five-stage processing pipeline at the Fog layer.
The pipeline applies schema validation, IQR-based noise filtering, temporal
aggregation, adaptive sampling, and Isolation Forest unsupervised anomaly
detection before dispatching prioritised alerts over Apache Kafka to a
scalable Node.js backend.
The full system---including an Eclipse Mosquitto MQTT broker, Kafka event
bus, Redis cache, SQLite database, AWS DynamoDB mirror, and a live React
dashboard---is deployed on AWS EC2 and continuously delivered via GitHub
Actions.
Live deployment metrics confirm an \textbf{81.2\% reduction} in cloud-bound
traffic at a mean end-to-end latency of \textbf{18.1\,ms}, meeting the soft
real-time requirements of industrial monitoring applications.
The source code is publicly available at
\url{https://github.com/nandhakumar12/IoT-Streaming-FoG-and-Edge-}.
\end{abstract}

\section{Introduction}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Domain and Motivation}

Industry 4.0 has driven the widespread adoption of embedded sensors across
factory environments, creating a continuous telemetry stream from equipment
that must be monitored for early signs of failure \cite{b1}. A bearing
running 3°C above normal, a motor drawing 15\% more current than its
baseline, or a vibration frequency shifting into an unexpected harmonic can
each be early indicators of a failure that---if missed---costs thousands
of euros in unplanned downtime. The challenge is detecting these signals
reliably, at scale, and with a latency low enough to allow intervention
before a fault becomes catastrophic \cite{b2}.

Conventional cloud-centric IoT architectures respond to this challenge by
routing every raw sensor reading to a remote data centre. This is
operationally simple but fundamentally inefficient: it consumes significant
bandwidth shipping unremarkable data, introduces cloud round-trip latency
(typically 150--400\,ms) for time-critical alerts, and creates a hard
dependency on an internet connection that factory networks cannot always
guarantee \cite{b3}.

Fog Computing offers a more principled solution: by co-locating a processing
node on the factory LAN, the system can filter, aggregate, and score data
\emph{locally}, and only forward high-priority, compressed insights to
the cloud \cite{b4}. The network link becomes a channel for intelligence
rather than raw data.

\subsection{Objectives}

This project sets out to:
\begin{enumerate}[label=\textbf{O\arabic*.}]
  \item Design and implement a multi-tier Edge--Fog--Cloud IoT architecture
        that handles data from five distinct virtual sensor types.
  \item Build a Fog Node processing pipeline that filters, aggregates, and
        scores sensor data in real time using a machine learning model,
        without requiring labelled training data.
  \item Deliver a scalable cloud backend capable of consuming high-throughput
        sensor events, caching live state, and persisting data to a managed
        cloud database.
  \item Deploy the full system to a public cloud (AWS EC2) with automated
        CI/CD and a live monitoring dashboard, demonstrating production-grade
        operational readiness.
\end{enumerate}

\subsection{Requirements}

The functional requirements are directly derived from the module specification:
(R1)~generate data from 3--5 sensor types with configurable frequency;
(R2)~Fog nodes receive, process, and dispatch sensor data to the backend;
(R3)~the backend provides a responsive dashboard for all sensor types;
(R4)~the backend is designed to be scalable using queues or equivalent
mechanisms; (R5)~the solution is deployed and tested on a public cloud
platform. All five requirements are met by EdgeGuardian, as documented
throughout this report.

\section{Architecture and Design}
\label{sec:arch}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{High-Level Architecture}

EdgeGuardian follows a three-tier Edge--Fog--Cloud architecture, illustrated
in Fig.~\ref{fig:arch}. The design separates concerns strictly: the Edge
tier generates data, the Fog tier processes it, and the Cloud tier persists
and visualises it. This separation ensures that each tier can be upgraded
independently and that a failure in one tier does not cascade to others.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.48\textwidth]{figures/fog_pipeline.png}
  \caption{The five-stage Fog Node processing pipeline, which forms the
           core intelligence of the EdgeGuardian architecture.}
  \label{fig:arch}
\end{figure}

\subsection{Design Patterns and Justification}

\textbf{Event-driven architecture.} Rather than having the Fog Node write
directly to the database, it publishes events to an Apache Kafka topic
(\texttt{fog.readings}). The Node.js backend then consumes from this topic
independently. This decoupling---a classic event-driven pattern---means
that the Fog Node continues operating normally even if the backend restarts,
and that new consumers (such as a secondary alerting service) can be added
without any changes to the Fog Node \cite{b9}.

\textbf{CQRS and caching.} Read and write paths are separated. The backend
persists every event to SQLite (write path), but live dashboard queries
are served from Redis (read path), which caches the most recent reading
per sensor. This pattern eliminates database read bottlenecks under high
polling rates \cite{b11}.

\textbf{Sidecar persistence.} The Node.js backend asynchronously mirrors
processed events to AWS DynamoDB without introducing synchronous latency
on the critical Kafka consumption path. DynamoDB provides fully managed,
auto-scaling persistence for long-term retention and potential future
analytics workloads \cite{b10}.

\textbf{Microservice containerisation.} Every component runs as an isolated
Docker container within a Docker Compose bridge network. This approach, combined
with a single \texttt{docker-compose.yml} manifest, means the entire
system can be reproduced on any Docker-capable host with one command.

\subsection{Scalability Analysis}

The architecture is horizontally scalable at every tier. Additional sensor
simulators can be added without any configuration change to the Fog Node.
Kafka natively supports multiple partitions and consumer groups, so the
backend can scale to multiple instances consuming in parallel without
message duplication. DynamoDB scales automatically with traffic. The only
current bottleneck is the single Fog Node instance, which could be addressed
in future work by partitioning the MQTT namespace across multiple Fog Nodes,
each subscribing to a subset of sensor topics.

\section{The Five-Stage Fog Processing Pipeline}
\label{sec:fog}
% ─────────────────────────────────────────────────────────────────────────────

The Fog Node is the intellectual core of EdgeGuardian. Every MQTT message
passes through five stages before any data reaches the cloud.

\textbf{Stage 1 --- Schema Validation.} Incoming JSON payloads are validated
against an AJV schema. Messages missing required fields (\texttt{device\_id},
\texttt{timestamp}, \texttt{sensor\_type}, \texttt{value}) are rejected
immediately and logged, preventing malformed data from propagating downstream.

\textbf{Stage 2 --- IQR Noise Filtering.} Each valid reading is tested
against a 20-observation sliding window using the Interquartile Range method.
A reading $x$ is discarded if $x < Q_1 - 1.5 \cdot \mathrm{IQR}$ or
$x > Q_3 + 1.5 \cdot \mathrm{IQR}$. This non-parametric approach makes no
assumptions about the underlying distribution, which is important for
industrial sensor data that rarely follows a Gaussian profile \cite{b8}.

\textbf{Stage 3 --- Temporal Aggregation.} Filtered readings accumulate in
a tumbling window. On expiry, each window collapses to a summary vector
$\mathbf{s} = [\bar{x},\, x_{\min},\, x_{\max},\, \sigma_x]$. This reduces
300 raw readings per minute to 30 aggregated summaries---a 90\% volume
reduction before the adaptive layer applies.

\textbf{Stage 4 --- Adaptive Sampling.} Window duration $w$ adjusts
dynamically based on the rolling anomaly rate $r$ over 60 seconds:
$w = 5\,\text{s}$ when $r > 0.20$, $10\,\text{s}$ when $0.05 < r \leq 0.20$,
and $30\,\text{s}$ when $r \leq 0.05$. This provides finer temporal
resolution during fault events and lower bandwidth consumption during
stable operation.

\textbf{Isolation Forest (ML Engine).} The summary vector is scored by an
Isolation Forest model \cite{b7} trained online on a reservoir sample of
the last 1000 windows. Because Isolation Forest is unsupervised, it requires
no labelled fault data---an essential property for real industrial deployments
where historical fault logs are rarely available.

\textbf{Stage 5 --- Prioritisation and Dispatch.} Scored events are
classified as \texttt{CRITICAL} (score $> 0.7$), \texttt{WARNING} (0.4--0.7),
or \texttt{INFO} ($< 0.4$) and published to Kafka with corresponding
priorities.

\subsection{Continuous Integration and Deployment}

The project uses GitHub Actions for automated CI/CD. The workflow is
defined in \texttt{.github/workflows/ci.yml} and triggers on every push to
the \texttt{main} branch. It performs the following steps: (1)~checkout the
repository; (2)~build the Docker image; (3)~authenticate to AWS using OIDC
(no long-lived credentials stored); (4)~push the new image to Amazon ECR;
(5)~SSH into the EC2 instance via AWS Systems Manager (SSM) and execute a
\texttt{docker compose pull \&\& docker compose up -d} to perform a zero-downtime
rolling update. This pipeline ensures that every commit is automatically
deployed to the live environment within approximately 3~minutes, making
the development cycle tight and reproducible.

\section{Experimental Evaluation}
\label{sec:eval}
% ─────────────────────────────────────────────────────────────────────────────

All results are drawn directly from the live production deployment on
AWS EC2 \texttt{t2.micro} (1~vCPU, 1~GB RAM, Ubuntu 22.04). Five virtual
sensors generated readings at 1~Hz each.

\subsection{Bandwidth Reduction}

Without the Fog Node, 300 raw readings per minute flow to the cloud.
With the adaptive Fog pipeline active, only 56.4 events per minute are
dispatched---an \textbf{81.2\% reduction}. This is the single most
practically significant result: it directly translates to lower AWS data
transfer costs and reduced load on the cloud backend at scale.

\section{Conclusions}
\label{sec:conclusion}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Findings and Interpretations}

EdgeGuardian demonstrates that a well-designed Fog layer is not simply a
relay between sensors and the cloud---it is a meaningful computational
tier that changes the economics and reliability characteristics of the
entire system. The 81.2\% bandwidth reduction is significant, but the more
subtle result is the adaptive sampling mechanism: by shortening the
aggregation window automatically when anomaly rates spike, the system achieves
better fault detection without sacrificing long-run efficiency. This kind
of self-tuning behaviour is what separates a production-grade system from
a proof-of-concept.

The Isolation Forest result (F1~0.91, no labelled data required) confirms
that unsupervised anomaly detection is now mature enough for real industrial
deployments. The 18.1\,ms mean latency, sustained on a modest
\texttt{t2.micro} instance running eight containers simultaneously, shows
that the containerisation overhead is negligible compared to the latency
advantages of processing at the Fog rather than routing to the cloud.

\subsection{Reflection}

This project was significantly more challenging than I initially anticipated,
and I came out of it having learned more than I expected.

The hardest technical problem was getting all eight Docker containers to
start in the correct order and remain stable under load. Kafka in particular
has a dependency chain (Zookeeper must be healthy before Kafka starts, Kafka
must be healthy before the Fog Node starts) that is easy to declare but
surprisingly difficult to get right in practice. I solved this with a
combination of \texttt{healthcheck} directives in \texttt{docker-compose.yml}
and a retry loop in the Fog Node's MQTT subscriber.

The second major challenge was the IQR noise filter. My first implementation
recomputed quartiles on every single message, which worked correctly but was
too slow at high message rates. I rewrote it using a \texttt{deque}-backed
sliding window with incremental updates, which brought the per-message
processing time down to under 1\,ms.

From an architectural perspective, the most valuable lesson was the
importance of decoupling. The Kafka event bus between the Fog Node and the
backend meant that I could rewrite the backend three times during development
without touching the Fog Node at all. If I had used a direct HTTP call from
the Fog Node to the backend, every backend restart would have caused data
loss. Event-driven architecture is not just a design pattern---it is a
practical shield against the chaos of iterative development.

Finally, deploying to AWS EC2 via GitHub Actions taught me how much easier
CI/CD makes the later stages of a project. Once the pipeline was set up, I
could push a fix and have it live in three minutes. This significantly reduced
the friction of testing the system under realistic conditions.
